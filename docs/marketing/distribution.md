## Rules and prerequisites

### r/ClaudeAI

[The subreddit rules](https://www.reddit.com/r/ClaudeAI/about/rules.json) expressly permit educational project showcases by their creators when the project was made with or for Claude. They require a description, details of Claude's role, free trial availability, restrained promotional language, no referral links, and suitable flair. Feed posting requires OP karma greater than 100. Do not manufacture a build story or claim this agent built the software. Hangar is free software, but using hosted Claude or ChatGPT may require the user's existing subscription; say that clearly. Include an honest limitation and one specific feedback question. Recheck recent posts to avoid duplicating a recent showcase. Voting manipulation is prohibited.

### r/selfhosted

[The current rules](https://www.reddit.com/r/selfhosted/about/rules.json) require self-hosting relevance, documented and production-ready promoted applications, and restrained self-promotion. Projects with a first public presence less than three months ago belong only in the current New Project Megathread. Local git history starts October 25, 2026; absent earlier public evidence, January 25, 2027 is the earliest three-month milestone. Recheck timestamp and rules before a standalone post. The Wednesday exception for dashboards does not override the new-project rule. Search for the current pinned megathread at publication time rather than reusing a stale thread URL.

### Hacker News

[Show HN rules](https://news.ycombinator.com/showhn.html) require runnable work, the actual maker's involvement, and accessibility for experimentation. [General HN guidelines](https://news.ycombinator.com/newsguidelines.html) prohibit generated/AI-edited text, automated posting, vote solicitation, and delete-and-repost tactics. These requirements mean campaign drafts must not be pasted or AI-edited into HN. The founder should independently write about their actual motivation, design tradeoffs, prerequisites, and limitations. Use the repository as the destination, with a verified quick start and actual screenshots. This channel has high potential audience fit but uncertain distribution; no timing trick guarantees a front-page result.

### selfh.st

[About selfh.st](https://selfh.st/about/) identifies its weekly newsletter and application directory as self-hosting discovery resources. [Submit Content](https://selfh.st/submit/) is the appropriate intake route. The retrieved page did not reveal form eligibility, fields, or editorial lead time; do not invent requirements or promise inclusion. Check the live page before entering a submission. Use the unpaid editorial route only, with no sponsorship purchase or cold outreach campaign.

### DEV

[DEV's content policy](https://dev.to/terms) requires substantial, relevant content and prohibits content primarily intended for promotion or backlinks. Explain a useful workflow in the article itself; readers should learn how it works without following the repository link. An appropriate article would cover the process lifecycle, actual installation, reconnect demonstration, and the network exposure boundary. Use only claims confirmed in the shipped release.

### Curated lists

[Awesome Claude Code's rules](https://github.com/hesreallyhim/awesome-claude-code/blob/main/CONTRIBUTING.md) require either 14 days since the default branch's first commit plus development on later days, or 100 stars. They require a human-authored recommendation using the web issue template and explicitly reject PR/CLI submission routes. One resource recommendation at a time; selection is discretionary. A project requiring signup/payment may need stronger adoption evidence, so disclose the distinction between the free application, optional local models, and external hosted subscriptions.

[Awesome Selfhosted's rules](https://github.com/awesome-selfhosted/awesome-selfhosted-data/blob/master/CONTRIBUTING.md) require a first release older than four months, reject software dependent on one specific cloud provider, and prohibit LLM-generated contributions. Do not submit this file or a generated listing. Revisit after maturity and have a human assess fit and author any contribution independently.

## Publication readiness and cadence

Before the first public launch, verify the Docker quick start from a clean environment; demonstrate a session surviving a closed browser; capture desktop and phone views with secrets removed; confirm license, tagged release, and issue-report route. State the owner-account model and private-access guidance accurately. Avoid claiming a public demo is available: a shared authenticated demo would expose a shell.

Start with one qualified community post, answer installation questions, and fix recurring friction before the next channel. Allow 24–48 hours for learning between launches; this is an operating cadence, not a platform requirement. Keep at least an hour available after each post and check replies again the following day. Publish each channel once unless a genuinely substantive update and its rules justify another post. If the founder lacks a required account or karma, use the next eligible channel rather than creating activity to bypass the gate.

Record destination, timestamp, live URL, maintainer identity, exact revision promoted, GitHub stars before/after 24 and 72 hours, referral traffic when available, installs or issues, and useful feedback. GitHub star changes alone do not prove which post caused them. Continue the channels that bring qualified users; improve onboarding if visitors arrive but cannot install. None of these routes guarantees 100 stars or a deadline.
